# Code scan, 2026-10-30 (open findings)

A read-only scan of the whole repo after FP-300 and the R7–R9 work: security, correctness,
broken project rules, calls to things that don't exist, copy-paste drift, and dead code.
**Nothing here is fixed yet.** Each item is tracked in `FIXLOG.md` ("Open from the
2026-10-30 scan") with the ID below; fix them with the usual workflow
(`.claude/skills/fix-and-build/`) and move each to an entry in FIXLOG when done.

How it was checked: each area was reviewed by an agent reading the code, and the main claims
were then re-read in the code by the main session. Items marked *(scan)* were confirmed by the
agent reading the code but not re-read separately. Line numbers are as of commit `ea0006b`.

## Security

### S13 (high): any merchant can read another merchant's transactions
- Where: `apps/api/src/reporting/scope.ts:8-19`, used at `apps/api/src/routes/reporting.ts:37`.
- What: `resolveReportMerchantId` accepts a `merchantId` from the filter if that merchant is a
  split child of *any* parent. It never checks that the caller is that parent.
- Exploit: any merchant session (any role), API key or impersonation grant calls
  `GET /v1/reporting/transactions?filter={"merchantId":"<other merchant's id>"}` and gets up to
  500 of that merchant's transactions (id, status, amounts, reference, time). The local database
  has 288 split-child merchants.
- Suggested fix: add `AND parent_merchant_id = <caller>` to the lookup, or drop the parameter.

### S14 (high): SSRF through webhook URLs
- Where: `apps/api/src/webhooks/create.ts:15-29` (`validateWebhookUrl`), `webhooks/transport.ts:39`,
  `webhooks/testSend.ts:70`, `webhooks/dispatcher.ts:188`.
- What: only the scheme is checked (https only in production). Private, loopback and link-local
  addresses aren't blocked, and `fetch` follows redirects. The test-send route returns the first
  2 000 characters of the response; the delivery log keeps them too. A code comment says private
  IPs are blocked; they aren't.
- Exploit: an owner or finance user registers `https://attacker.example/x`, which redirects to
  `http://169.254.169.254/latest/meta-data/...`; `POST .../webhook-endpoints/:id/test` returns the
  cloud metadata (credentials). In development mode plain `http://` internal hosts work directly.
- Suggested fix: resolve the host and reject private/loopback/link-local/metadata ranges at
  create time and again at send time; `redirect: "manual"`; don't echo response bodies.

### S15 (high, deploy): the compose stack is not production-safe
- Where: `ops/docker-compose.yml`, `ops/Dockerfile.node`, repo root (no `.dockerignore`).
- What *(scan)*: the api service sets no `NODE_ENV`, so it runs in development mode. Login
  responses then return the OTP code, the acquirer callback secret is empty (callbacks can be
  forged), the public dev webhook key is used, and cookies aren't marked Secure. Postgres is
  published on `5432` with the dev password. The Node container runs as root.
- Confirmed: there is no `.dockerignore`, so `COPY . .` puts `ops/.env.docker` (the real
  acquirer secret) and `.git` into the image.
- The compose comments say the hosted demo box runs this same file.
- Suggested fix: production env (`NODE_ENV=production`, real secrets from an env file/secret store),
  a `.dockerignore`, don't publish 5432, `USER node`.

### S16 (medium): the OTP guess limit resets on every login, and nothing is rate-limited
- Where *(scan)*: `apps/api/src/routes/auth.ts:55-100`, `routes/adminAuth.ts:54-110`.
- What: each `/login` creates a fresh challenge with 5 new attempts (S9 only carried the count
  over on resend), and no rate-limit plugin is registered.
- Exploit: someone holding a merchant or admin password loops login → 5 guesses; a 6-digit code
  falls after roughly 200 000 logins. Passwords can also be guessed without limit.
- Suggested fix: rate-limit login and OTP verification per account and per IP; cap OTP attempts per
  account across challenges.

### S17 (low–medium): the public pay endpoint can be used to test stolen cards
- Where *(scan, likely)*: `POST /v1/payment-links/:token/pay`.
- What: no login, no rate limit, and a decline frees the link for another attempt.
- Suggested fix: per-link and per-IP attempt limits; lock the link after N declines.

### S18 (low): an unsalted hash of card number, CVV and expiry is stored
- Where *(scan)*: `apps/api/src/payments/authorize.ts:51` (the idempotency `request_hash`).
- What: SHA-256 of `{pan, cvv, expiry}` can be brute-forced, and keeping CVV-derived data breaks
  the card-industry (PCI) rule against keeping CVV after authorization. The cards are simulated
  today.
- Suggested fix: hash a keyed HMAC of a token/last-4, never the CVV.

### S19 (low): smaller auth gaps
- `GET /v1/reporting/export-summary` (`routes/reporting.ts:79`) has no `requireMerchantAuth`; it
  reads `request.merchantAuth!` and crashes with a 500 rather than leaking (confirmed).
- *(scan)* Impersonation grants aren't checked against the admin's account status
  (`admin/impersonation.ts:119`), so a disabled admin keeps read access for up to 15 minutes.
- *(scan)* Neither merchant nor admin login issues a new session token after the OTP step
  (session fixation; needs a planted cookie to exploit).
- Known already (S8): a merchant user with the support role can capture and void payments.

Checked and found clean: cross-tenant checks on transactions, events, batches, payment links,
webhooks, KYC files, API keys and refunds; admin role gates (including the R7–R9 recovery routes);
CORS allowlist and CSRF (SameSite=Lax plus JSON bodies); SQL parameterisation; KYC file paths; CSV
export escaping; the settlement internal API's token check; the Go container runs as nonroot.

## Bugs

### M21 (high): TypeScript and Go compute a discounted merchant's fee differently
- Where: `apps/settlement/internal/settlement/discounted_fee.go:15-24` (used by `CloseBatch`
  `batch.go:215` and `RecalculateMDR`, including F20's `batchRefundFees`) vs
  `apps/api/src/payments/capture.ts:196`, `payments/discountAdjustment.ts:59`, `fees/estimate.ts`,
  `settlement/query.ts`.
- What: TypeScript charges `round(amount × mdr)` and then refunds `round(fee × discount)`. Go
  discounts the amount first and then charges `round((amount − round(amount × discount)) × mdr)`.
  These are two different roundings, which breaks ADR-0001's single-rounding rule; M13 fixed only
  the TypeScript side.
- Examples (250 bps, 10 % discount): 10 200 fils → TypeScript keeps 229, Go charges 230 (the
  merchant is paid 1 fil short); 1 000 fils → 23 vs 22 (overpaid by 1). Payout, ledger and
  reconciliation end up 1 fil apart per affected capture.
- Docs disagree as well: `docs/ARCHITECTURE.md:55` says the discount reduces the amount, while
  `discountAdjustment.ts` applies it to the fee.
- Suggested fix: make Go match the TypeScript/ledger order; add a test that compares Go's fee with
  what capture actually booked.

### R10 (high): the reporting consumer can skip outbox events for good
- Where: `apps/reporting/src/consumer/runConsumerPass.ts:64-71` (`WHERE id > cursor`).
- What: `outbox_events.id` comes from a sequence at insert time, not at commit time. If a
  transaction with id 100 commits after one with id 101 and a pass runs in between, the cursor
  moves to 101 and event 100 is never applied: that capture, refund or batch never reaches
  `merchant_daily_volume`. The comment calling the ids "monotonic" is wrong about commit order.
- Suggested fix: only read events older than a safety lag, or track processed ids
  (or use `pg_current_xact_id`/`xmin` ordering).

### X15 (medium): the admin "Rebuild analytics" button double-counts
- Where: `apps/api/src/admin/reportingRebuild.ts`.
- What: it truncates and rebuilds the rollups from source tables but doesn't move the consumer's
  cursor (the CLI rebuild resets it and replays). Events the consumer hasn't reached yet are then
  applied on top: 10 pending captures of 5 000 fils add 50 000 fils too much. It also buckets by
  `te.occurred_at` where the consumer uses the outbox `created_at`.
- Suggested fix: set the cursor to the current max outbox id in the same transaction, or make the
  button call the CLI's replay path.

### D6 (medium): in compose, every admin settlement action fails
- Where: `ops/docker-compose.yml` (token set on `settlement` only, line 101),
  `apps/api/src/config.ts:194` (defaults to `""`), `apps/settlement/internal/internalapi/server.go:184`.
- What: the API sends an empty bearer token, so run-batch, rebuild-balances and MDR recalculation
  from the admin console get 401. `ops/README.md:62`, the compose comment (line 95) and
  `docs/ARCHITECTURE.md:90` say the token "defaults to dev-token"; neither service has that
  default. D5 added the token to one side only.

### X16 (low): payout trends can stay "closed" forever
- Where *(scan, likely)*: `apps/reporting/src/consumer/applyEvent.ts:83-117`.
- What: `merchant_payout_trends` takes the batch status only when it applies
  `settlement.batch_closed`, and the consumer doesn't subscribe to `settlement.paid`. A pass that
  runs between close and payout stores `closed, paid_at NULL`, and only a rebuild corrects it.

### T5 (low): the admin Settlement page pre-fills the wrong date
- Where: `apps/admin/src/pages/settlement/SettlementPage.tsx:19-23`.
- What: "yesterday" is taken in the browser's local time and converted with `toISOString()`
  (UTC). At 01:00 Bahrain time on 30 Oct it pre-fills 2026-10-28 instead of the 29th. That ignores
  the Bahrain-business-day rule (ADR-0003).

## Copy-paste drift

- The fee discount order: M21 above.
- MDR recalculation uses `merchants.mdr_bps` only (`recalculate_mdr.go:57`), while capture and
  batch close use the dated `fee_schedules` rate minus the volume-tier bonus. Already recorded under
  M8 ("proper fix" not done).
- The dead `apps/api/src/v1/fees/calculateFee.ts:29` rounds half-up where `packages/money` and Go
  round half-to-even (20 fils at 250 bps: 1 vs 0). Not reachable (X18).
- The volume-tier bonus is read at capture time in TypeScript but at batch close in Go, so on the
  day the tier changes the two sides price 15 bps apart (an inline comment notes it; not in FIXLOG).
