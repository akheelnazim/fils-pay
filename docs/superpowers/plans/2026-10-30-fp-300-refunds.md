# FP-300 Refunds Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merchants can refund a captured payment (full or partial) from the dashboard or API, and the money is right everywhere: ledger, fee reversal, next payout, webhook, reports and reconciliation.

**Architecture:** The refund helpers already exist (`payments/processRefund.ts`, `refunds/initiateMerchantRefund.ts`, `refundState.ts`, `refundValidation.ts`) but are never called and carry the audit's bugs F1–F5, F12, F14. Each gap is fixed in its own branch and squash commit (`feat/FP-300-<F#>` → `feat(FP-300/<F#>): …`), then the route is wired, then the downstream consumers (webhook, settlement, reporting, reconciliation, API shape) learn about refunds. One end-to-end test closes it.

**Tech Stack:** Fastify + pg (TS, `node:test` via `npx tsx --test`), Go 1.22 + pgx (settlement), Postgres 16.

**Spec:** `fix-docs/filspay-audit-findings.md` §6 (F1–F13), FIXLOG row F14, `docs/meetings/2026-07-08-finance-eng.md` §4 (Huda's rules).

## Global Constraints

- Money is integer fils (1 BD = 1000 fils). No floats; use `@filspay/money` in TS, `money.Fils`/`int64` in Go.
- Settlement/business day = midnight to midnight Asia/Bahrain (UTC+3).
- ADRs in `docs/adr/` are binding. ADR-0005 reserves migrations 0054–0056; next free migration is **0080** (0078–0079 used by R3/R2).
- Huda: "reconciliation still ties out after refunds"; MDR reversed proportionally; total reversed across partials never exceeds the original fee; "a transaction is refunded when every fils we captured went back".
- Every task: failing test first (`<name>.fix.test.ts` / `<name>_fix_test.go`), smallest fix, callers checked in TS and Go, Sonnet reviewer before commit, FIXLOG row + entry, git flow from `fix-docs/memory/` (branch, pull, squash, push, delete branch, `Conflicts:` line if any).
- Never run `scripts/` against data.

## Review Focus

1. Two refunds on the same transaction at the same moment: only what was captured may go back in total (F3 test).
2. Refunds in a day bigger than that day's captures: the payout must not go negative and the debt must not vanish (F8 test: leftover refunds roll into the next batch).
3. Several partial refunds: fee reversed sums to exactly the original net fee, never more (F5 test).
4. Acquirer declines or is down after the amount was reserved: the reservation is released and a retry works (F3 test).
5. A refund made at 23:30 Bahrain time lands on that Bahrain day in reports and settlement, not the UTC day (F9 and F8 tests).
